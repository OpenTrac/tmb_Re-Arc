# AGENTS.md

This file contains contextual information about this repository for
LLM agents.

## Background

Given a target binary executable (`disks/SCUS_971.01`) compiled for the
PlayStation 2 (PS2) hardware platform, this repository attempts to:

- heuristically split the binary into the object files representing the
  C/C++ translation units (TUs) of the original source code
- disassemble the objects into human-readable MIPS R5900 (Emotion Engine)
  assembly code
- replace individual objects piece-meal with new objects
  (compiled from C/C++ code) which have 100% matching assembly code and variables
- link the mixed objects back together into an executable that 100% matches the
  original

This process allows us to eventually reproduce the source code of a binary while
statically guaranteeing that we match the original binary's behavior.
(If the generated ASM is identical, the behavior must be identical by extension.)

The primary tool used for this is `splat`, a Python package that supports this
process. Given some info about the binary and a set of "segments" declared in a
config file, `splat` splits up the segments, disassembles them into assembly code,
and creates a linker script that pieces them back together.

## Layout

- `src/`: C/C++ source code of the repository.
- `include/`: C/C++ includes for the repository.
- `config/`: `splat` configuration files, `objdiff` report, and `splat`-generated
  linker script.
- `build/`: Build directory.
- `asm/`: Contains MIPS assembly code disassembled from the target binary.
  - `matchings/`: MIPS disassembly of individual functions which have been
    100% matched to C/C++ code.
  - `nonmatchings/`: MIPS disassembly of individual functions which do not
    have 100% matching C/C++ equivalents yet.
- `tools/build_system/`: Python build system which runs various commands to
  split the binary and generate a Ninja build script.

## Usage

- `uv run configure.py generate`
  - Split the original binary using `splat` and generate the Ninja build system.
- `ninja`
  - Build the repository into a binary that attempts to match to the original.
    A `NONMATCHING` failure typically indicates that a C function does not match
    its disassembled MIPS equivalent in the original binary.
- `uv run configure.py distclean`
  - Resets the repository for a clean build. Useful if the repository appears
    to be in an invalid state.

## Constraints

### Matching

When attempting to match code, check [QUIRKS.md](QUIRKS.md) to see a list of
known compiler issues and memes/quirks for this repository which may prevent
some code from matching without further refinement.

If you come across an undocumented compiler quirk while matching code,
ask the user to document it in this file. Avoid writing sections and summaries
in `QUIRKS.md` directly; see the `Documentation` constraints in this file for why.

### Tooling

- Never edit the following files:
  - `asm/`: auto-generated by `splat`
  - `objdiff.json`: auto-generated by `configure.py`
  - `config/US/SCUS_971.01.ld`: auto-generated by `splat`
  - `config/US/report.json`: auto-generated by `objdiff`
  Editing these files can either cause un-debuggable build system errors or
  make the progress report inaccurate.
- After modifying any of these files, rerun `uv run configure.py generate`
  to regenerate the build system:
  - The build system itself (`tools/build_system/`)
  - The `splat` configuration file (`config/US/SCUS_971.01.yaml`)
  - Symbol lists in `config/` (`reloc_addrs.txt`, `symbol_addrs.txt`, `undefined_funcs.txt`)
- All Python commands should be run in the local virtual environment, found
  at `.venv/`.
  - `uv run` will do this automatically.

### Code

- After modifying any C/C++ code or headers, run `clang-format` to lint and format the
  generated code.
- The `ninja` build is the source of truth.
  If the build declares `NONMATCHING`, the binary is nonmatching,
  even if the current target function appears to be 100% matching.
- Avoid modifying the build flags unless necessary for experiments, as they are
  generally accurate.
  - The source of truth for these flags is `tools/build_system/env.py`.
  - If you temporarily modify `build.ninja` to test a specific flag with a TU,
    ensure that you also run `uv run configure.py generate` afterwards to make
    the build system consistent.
- Make sure that any `INCLUDE_ASM` or `INCLUDE_RODATA` macros
  generated by splitting a `splat` segment are using relative paths which
  start from `asm/`.
  Absolute paths should not be committed as these are system-specific.

#### Comments

- **Do not dump context into code comments.**
  - It is **critical** that the code in this repository stays human-readable.
    This repository moves rapidly. Comments may become outdated immediately after
    being written.
- **In general, keep code comments to a minimum.**
  - Do not write large comments which explain *what* is happening in the code.
    This should not be needed if the code is human-readable.
  - Comments that explain *why* something is necessary are useful.
    - However, these should be minimized to code blocks that are incomprehensible
      even for an experienced engineer, or for clear bugs/undefined behavior
      in the original ASM code.
- When writing comments, **avoid jargon while keeping them technical.**
  - Example of bad comments:
    ```
    /* R5900 opcodes with no C spelling.  Defined in this member. */
     #define SYNC() __asm__ __volatile__("sync" : : : "memory")
    /* COP0 Status ($12), bit 16 = interrupts enabled.  Taken as an lvalue: the
      wrappers mask the word in place. */
    #define MFC0_STATUS(dst) __asm__ __volatile__("mfc0 %0, $12" : "=r"(dst))
    #define COP0_STATUS_EIE 0x10000
    ```
    - "spelling" is not a common way to describe "code format" in programming.
    - The word "member" in this context is nonsensical at first glance;
      it presumably means `TU` (translation unit).
      If it does mean `TU`, the phrase `Defined in this member` is tautological
      and therefore extraneous.
    - The `COP0_STATUS_EIE` comment is mixed up with `MFC0_STATUS`.
    - The phrase `Taken as an lvalue` is accurate but not useful here.
      The average reader does not know what an `lvalue` is, and the readers who do
      know can see it very clearly.
    - `the wrappers mask the word in place` is not a useful comment here. It
      should go wherever the `wrappers` are (and probably shouldn't exist at all).
  - Example of better, revised comments:
    ```
    /* R5900 opcodes with no C equivalent. */
    #define SYNC() __asm__ __volatile__("sync" : : : "memory")
    #define MFC0_STATUS(dst) __asm__ __volatile__("mfc0 %0, $12" : "=r"(dst))

    /* COP0 Status, bit 16 (interrupts enabled).
    #define COP0_STATUS_EIE 0x10000
    ```
- When formatting comments or documentation,
  **prefer bulleted lists over dense comma-separated lists.**
  - Example of a badly-formatted list:
    ```
    One source per unique function (Phase 35): 102,991 function bodies written once in C (3,173 of them shared headers instantiated 262,594 times); 139 duplicate copies remain in 41 ledgered classes (declaration conflicts left for the types phase); 38 functions whose bytes vary per binary share one text through the text tier (2,030 sites); 1,645 same-address copies of 377 tiny bodies inside the cross-address classes are deferred to the names phase.
    ```
    This list is incredibly dense and full of parenthesized text, making it difficult to parse
    for both humans and LLMs.
    (It's also clearly an LLM context dump, which should never be added to this repo.
     We're ignoring that for this example.)
  - Example of a better-formatted list:
    ```
    One source per unique function (Phase 35):

    - 102,991 function bodies written once in C
      - 3,173 of them shared headers instantiated 262,594 times
    - 139 duplicate copies remain in 41 ledgered classes
      - Declaration conflicts left for the types phase
    - 38 functions whose bytes vary per binary share one text through the text tier
      - 2,030 sites
    - 1,645 same-address copies of 377 tiny bodies inside the cross-address classes
      are deferred to the names phase
    ```

#### Quality

- When decompiling assembly into matching C/C++ code, attempt to write the code as it may have
  been originally written. Avoid the following if possible:
  - `asm volatile` register pinning
  - Excessive manual pointer arithmetic (example: `*(type*)((u8*)ptr + offset)`)
  - Excessively complicated control flow (heavy `goto` usage)
  - Struct-to-pointer casts (struct accesses should be performed with `.` or `->`)
  - Excessive `void*` usage
    - If it's clear the original code used `void*` for polymorphism, use it as needed.

#### Organization

C/C++ source files in this repository are generally organized with the following
layout:

- Includes
- Macro definitions
- Struct definitions
- Global variables
- Function declarations (if needed)
- Function implementations

Follow this layout for newly written code.

Note that **the definition order of functions and variables matters**.
To match the original code, we must also match the order that variables and
functions were defined in.

### Documentation and Git

- **Never run `git commit` or generate a Git commit description.**
  - Commits must be reviewed by humans for this repository.
- **Never create a GitHub issue/pull request, or generate an issue/pull request description.**
  - Humans working on this repository are expected to understand the issues
    and PRs they submit.
- **Never generate documentation text files or Markdown files directly.**
  - Require the user to review your output and reformat it into their
    intended format themselves.
- If the user overrides you to generate any of the above, please add a
  watermark somewhere in the text: `(This text was generated via LLM.)`
  - It is critically important for us to separate human-written docs
    vs. LLM-written docs in this repository.
